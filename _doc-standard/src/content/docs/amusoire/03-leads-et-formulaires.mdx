## Le levier de routage

```js

```

## Tracking & provenance

**L'URL de la page = source unique de vérité.** Le script global injecte `page_uri` (= `window.location.href`, UTMs compris) dans tout `<form data-portal>` ; remontée dans la propriété contact `url_formulaire`, créée sur **les deux portails**. C'est elle qui dit d'où vient le lead et quel formulaire il a rempli. Les champs existants (Provenance, Comment connu…) restent en place pour le routage commercial.

| Module Make (`url_formulaire` mappé) | Route | Portal / Form |
| --- | --- | --- |
| 15 (+ fallback 23) | Flux Amusoire | `25692189` / `4df88a0c-…` |
| 26 (+ fallback 38) | Blindtest entreprises | `147562037` / `b108e60c-…` |
| 46 | Blindtest particuliers | `147562037` / `45cb43a7-…` |

<Callout type="piege" title="Piège — pageUri ≠ propriété">
  Le paramètre natif `Page URL / pageUri` du module Make n'est qu'une métadonnée de timeline : ni filtrable en liste, ni utilisable en workflow. La source exploitable est la propriété `url_formulaire` mappée dans la collection `fields`.
</Callout>

<Callout type="piege" title="Piège — cookie hutk">
  Le script de tracking chargé est celui du portail **25692189** → le `hubspotutk` lui appartient. Les forms du flux BLINDTEST reçoivent un `hutk` cross-portail ignoré. À aligner si on veut l'attribution parcours côté BLINDTEST.
</Callout>

## Récap simulateur dans HubSpot

En parallèle du mail Resend, un récap textuel de la simulation est écrit dans la propriété contact `simulation_roi__recap` (multi-line, form `4df88a0c-…`) : les commerciaux le retrouvent dans la fiche sans dépendre du mail. Mapping présent dans le module **15 et son fallback 23**.

<Callout type="danger" title="Danger — hutk vide = 400">
  Le champ « HubSpot Tracking Cookie » du module 15 doit rester **complètement vide**. Un `hs_context` vide envoyé comme hutk → `400 — is not a valid Hutk`, le module 15 échoue, seul le fallback 23 tourne : sans le mapping dans le 23, le récap n'arrive jamais.
</Callout>

- Contenu du récap en **ASCII pur** (ni accents ni €) : un copy-paste avait corrompu l'encodage (`reçue → reÃ§ue`). Pour modifier : taper directement dans Make.
- Champ ajouté côté form HubSpot invisible dans le mapper Make ? **Rafraîchir la structure** : module → champ « Form » → retirer puis re-sélectionner le form.

## Pièges des dropdowns

Un champ HubSpot de type menu déroulant rejette (ou stocke en valeur orpheline) toute valeur qui ne matche pas **caractère pour caractère**, casse comprise, une valeur interne. Webflow envoie l'attribut `value` de l'`<option>`, pas le texte affiché (le form UK affiche « Social media » mais envoie `Réseaux Sociaux`).

| Champ HubSpot | Type | Statut |
| --- | --- | --- |
| `etablissement` | dropdown | <Pill kind="ok">OK</Pill> 6/6 valeurs alignées |
| `heures_rappel` | texte libre | <Pill kind="ok">OK</Pill> aucune contrainte |
| `comment_vous_nous_avez_connu__` | dropdown | <Pill kind="warn">Corrigé</Pill> `Réseaux sociaux` ≠ `Réseaux Sociaux` — réaligné dans les 3 forms Webflow |

## Formulaire recrutement — Statut, Date de naissance, Secteur

Le form "Formulaire Recrutement" (`/pro-recrutement`) créait bien les contacts, mais 3 champs (`status`, `anniversaire_ou_date_de_naissance`, `zone_geographique_detaillee`) restaient vides sur la fiche HubSpot. <Pill kind="ok">Corrigé le 2026-08-06</Pill>

**Cause** : mapper du module `submitDataToFormV3` jamais mis à jour avec ces 3 champs à l'ajout du formulaire — oubli d'intégration, pas un bug du formulaire.

<Callout type="piege" title="Piège — collision de nom de champ générique">
  Ce scénario Make est un **catch-all partagé** entre plusieurs formulaires Webflow (simulateur, licences, recrutement…). Le champ Select "Secteur géographique" du form recrutement avait gardé son nom Webflow par défaut, `Field` — **exactement la même clé** qu'un champ Select du simulateur (jour de rappel). Mapper `Field` en dur aurait fait remonter "Mardi" dans la propriété secteur géographique selon quel formulaire déclenchait le scénario. Fix : renommer le champ dans le Designer Webflow (`Field` → `location`) plutôt que de filtrer côté Make — supprime la collision à la source.
</Callout>

| Champ Webflow | Type | Clé webhook |
| --- | --- | --- |
| Secteur géographique | Select | `location` *(renommé depuis `Field`)* |
| Statut | Select | `status` |
| Date de naissance | Plain | `date-of-birth` |

Mapping ajouté dans le module **15** (primaire) et son fallback **23** :

```
status                            = {{3.payload.data.status}}
anniversaire_ou_date_de_naissance = {{3.payload.data.`date-of-birth`}}
zone_geographique_detaillee       = {{3.payload.data.location}}
```

<Callout type="warn" title="Coquille connue, non bloquante">
  L'option Select `status` "Pas encoe de satut" contient une faute de frappe (au lieu de "Pas encore de statut") côté Webflow — ne matche aucune valeur de l'enum HubSpot. À corriger dans les settings du champ sur `/pro-recrutement`.
</Callout>

Validé le 2026-08-06 par soumission réelle sur `amusoire.com/pro-recrutement`, contact vérifié via l'API HubSpot (lecture directe par ID, pas seulement l'index de recherche qui peut avoir un délai de propagation).
