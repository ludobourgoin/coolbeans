Site Webflow, automatisations Make, CRM HubSpot (2 portails), emails Resend. 39 pages publiées (+ gabarits CMS), 6 formulaires, 1 simulateur sur-mesure, 1 popup opt-in. Un site de landing pages hérité (lp.pro.thisisblindtest.com) reste en ligne en attendant sa suppression.

Contexte & objectifs

Site vitrine + acquisition : réservation de salles privées côté grand public, démarchage d'établissements (bars, hôtels, campings…) pour la solution de licences.

  • Générer des leads B2C (réservations, événementiel) et B2B (licences).
  • Router chaque lead vers le bon CRM selon sa nature.
  • Rendre le client autonome sur le contenu sans casser le site.

Les interdits

🚫 À ne jamais faire
  • Pas d'emoji / caractères spéciaux dans les slugs.
  • Ne pas toucher aux champs techniques / ID (Make, Memberstack).
  • Laisser un champ vide plutôt qu'un espace.
  • Ne jamais renommer une classe ou un composant — casse le style partout.

Publier un article

  1. Save as Draft — sauvegarde sans publier.
  2. Stage for Publish — prêt pour la prochaine mise en ligne.
  3. Publish — ⚠️ publie tout le site.
Avertissement

« Publish » pousse tout le site en prod. En cas de doute, reste sur Stage for Publish et préviens Coolbeans.

Blog & CMS

Une seule collection Articles alimente deux listings : Actus (B2C) et Blog (licences, B2B). Un article n'apparaît que sur une des deux pages.

ChampRôle
« Quel blog ? »Route l'article : Actus ou Blog (licences). Le seul champ qui décide.
TagsPortent le même menu Actus / Blog — ne rattacher que des tags du même blog que l'article (sinon filtrage vide ou hors contexte).
« Catégorie »Label éditorial affiché (ex. Quiz musical) — aucun effet de routage.
Piège — article invisible

Tant que « Quel blog ? » n'est pas renseigné, l'article n'apparaît sur aucune des deux pages (les Collection Lists filtrent dessus). Premier réflexe si un article publié reste introuvable.

Checklist — publier sur la bonne page

  1. Renseigner « Quel blog ? » = Actus ou Blog (licences).
  2. Choisir une Catégorie (label affiché, sans effet de routage).
  3. N'ajouter que des tags du même blog.
  4. Publier l'article, puis publier le site pour rafraîchir le listing.

Modèle éditorial : titre → slug court (sans accent/emoji), catégorie obligatoire, meta title/description, alt text.

Tracking & provenance

L'URL de la page = source unique de vérité. Le script global injecte page_uri (= window.location.href, UTMs compris) dans tout <form data-portal> ; remontée dans la propriété contact url_formulaire, créée sur les deux portails. C'est elle qui dit d'où vient le lead et quel formulaire il a rempli. Les champs existants (Provenance, Comment connu…) restent en place pour le routage commercial.

Piège — pageUri ≠ propriété

Le paramètre natif Page URL / pageUri du module Make n'est qu'une métadonnée de timeline : ni filtrable en liste, ni utilisable en workflow. La source exploitable est la propriété url_formulaire mappée dans la collection fields.

Piège — cookie hutk

Le script de tracking chargé est celui du portail 25692189 → le hubspotutk lui appartient. Les forms du flux BLINDTEST reçoivent un hutk cross-portail ignoré. À aligner si on veut l'attribution parcours côté BLINDTEST.

Récap simulateur dans HubSpot

En parallèle du mail Resend, un récap textuel de la simulation est écrit dans la propriété contact simulation_roi__recap (multi-line, form 4df88a0c-…) — les commerciaux le retrouvent dans la fiche sans dépendre du mail. Mapping présent dans le module 15 et son fallback 23.

Danger — hutk vide = 400

Le champ « HubSpot Tracking Cookie » du module 15 doit rester complètement vide. Un hs_context vide envoyé comme hutk → 400 — is not a valid Hutk, le module 15 échoue, seul le fallback 23 tourne : sans le mapping dans le 23, le récap n'arrive jamais.

  • Contenu du récap en ASCII pur (ni accents ni €) : un copy-paste avait corrompu l'encodage (reçue → reÃ§ue). Pour modifier : taper directement dans Make.
  • Champ ajouté côté form HubSpot invisible dans le mapper Make ? Rafraîchir la structure : module → champ « Form » → retirer puis re-sélectionner le form.

Pièges des dropdowns

Un champ HubSpot de type menu déroulant rejette (ou stocke en valeur orpheline) toute valeur qui ne matche pas caractère pour caractère, casse comprise, une valeur interne. Webflow envoie l'attribut value de l'<option>, pas le texte affiché (le form UK affiche « Social media » mais envoie Réseaux Sociaux).

Note — pourquoi Resend

Le mail prospect passe par Resend, pas par HubSpot : l'add-on Transactional Email HubSpot coûte ~600 $/mois. Resend : délivrabilité équivalente, quota gratuit 3 000 mails/mois (100/jour), découplé du CRM.

Piège — palier max, pas la somme

Coût licence annuel = max(paliers cochés) × 12. Plusieurs objectifs cochés = une seule licence, la plus élevée. Ex : RDV + Privatif → max(159, 279) × 12 = 3 348 €, et non (159 + 279) × 12.

Gain net annuel = CA total − coût licence. À faire (reporté) : mention « tarif valable pour un engagement 24 mois » (confirmée le 2026-07-24), non implémentée.

Recalcul : au chargement, à chaque input/checkbox, au clic « Étape suivante » (délai 100 ms pour Inputflow), et quand le step ROI devient visible (MutationObserver) — les hidden inputs sont à jour au submit.

Bundle JS — intégration Webflow

TypeScript + esbuild (starter Finsweet), pnpm. Sortie : dist/index.js (~5 KB) + dist/index.css (~2,5 KB). Scripts : pnpm dev (watch + localhost:3000) · pnpm build · pnpm check · pnpm lint.

Inliné directement dans Webflow (pas de CDN) : le repo est privé (jsDelivr ne sert que le public) et l'inlining déploie immédiatement.

  1. Modifier le code dans src/ (ex. calculator.ts).
  2. pnpm build.
  3. Webflow → Pages → /pro/simulateur → Settings → Custom Code : dist/index.css dans <style> (head) · dist/index.js dans <script> (before </body>).
  4. Publish (staging d'abord).
Avertissement

Ne pas retirer les deux scripts InputFlow du head : ils gèrent [if-step="ROI"] et [if-element="button-next"] utilisés par le code custom.

  • required sur blocs masqués : géré par conditionalDisplay.ts (dataset.wasRequired) — ne pas retirer cette logique.
  • Checkbox RGPD : validation JS (validation.ts), ne pas réactiver required côté Webflow.
  • Coefficients business : toujours passer par les Custom Attributes, pas par le code.
  • Scénario Make : stable — le mail prospect = 3 modules (51/52/47) sur la route 3, pas de scénario séparé. Ne pas réécrire les branches existantes.

  • CTA : 4 URLs en dur dans la formule du module 52 — à mettre à jour si un calendrier change ou un commercial arrive.
  • API Key Resend : jamais dans le repo (module Make / coffre client).

Popup opt-in

Lib : Finsweet Attributes v1 (modal)MAJ : 2026-07-30Fréquence : 1 affichage / 7 jours

S'ouvre automatiquement après un délai sur certaines pages, plafonné à 1 affichage / 7 jours par visiteur. Indépendant du simulateur.

Architecture

BriqueOù elle vitRôle
Lib FinsweetProject Settings → Custom Code → Footer (global)Charge le moteur modal partout, une fois
Composant modalSource sur la page /modal, instance posée sur chaque page concernéeMarkup + contenu (trigger open-1, wrapper modal-1)
Script déclencheurFooter globalDécide quand / sur quelles pages ouvrir + cooldown

Éditer le contenu

  1. Ouvrir le composant modal (page /modal ou panneau Components) → Edit Component.
  2. Modifier texte / image / champ / bouton comme n'importe quel élément.
  3. Publish — répercuté sur toutes les instances du site.

Le wrapper modal-1 peut être en display:none au repos : Finsweet l'affiche à l'ouverture.

Modalités d'affichage

VariableValeur actuelleEffet
ENABLEDfalseInterrupteur global — true = actif partout, false = coupé
allowed10 chemins fixesPages exactes où le popup s'affiche (+ préfixe /actu/ pour tous les articles)
DELAY_MS8000Délai avant ouverture — démarre au chargement de la page
COOLDOWN_DAYS7Fréquence max / visiteur (localStorage, clé optin_popup_seen)
MAX_WAIT_MS15000Filet de sécurité (attente max de l'init lib) — ne pas toucher

Où trouver ENABLED : Project Settings → Custom Code → Footer code, bloc <!-- Pop up -->. Changer la valeur, puis Save + Publish.

Recettes courantes

  • Ajouter à une page : chemin dans allowed + poser l'instance du composant sur la page + Publish.
  • Retirer d'une page : enlever le chemin de allowed (l'instance peut rester).
  • Activer / couper partout : ENABLED à true/false — prévu pour les évènements ponctuels (fête de la musique…).
  • Délai / fréquence : DELAY_MS et COOLDOWN_DAYS.

Points de vigilance

  • Le composant doit être présent sur la page : allowed seul ne suffit pas — sans markup, le script sort en silence.
  • Lib chargée une seule fois en global — ne pas remettre le loader dans le composant.
  • Attributes v1 uniquement : jamais de v2 sur le site (incompatibles).
  • Cooldown pendant les tests : navigation privée ou localStorage.removeItem('optin_popup_seen').
  • Ne pas remplacer l'attente Finsweet (fsAttributes.push) par un .click() direct : race condition, le modal ne s'ouvrirait pas. Si l'init n'arrive pas, le cooldown n'est pas brûlé.
