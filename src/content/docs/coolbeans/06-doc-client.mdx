Le système qui fait exister cette page et toutes les docs clients : où vit
le contenu, qui voit quoi, et comment une doc se met à jour. Pour qui écrit
ou fait évoluer une doc.

## Ce que c'est

Chaque client a **une** doc, faite de pages, servie sur
`my.coolbeans.cc` derrière l'authentification. Un client ne voit que la
sienne ; les admins voient tout. Principe fondateur : 1 client = 1 doc — un
client qui accumule plusieurs projets enrichit la même doc, il n'y a jamais
de doc par projet.

## Ce que vous pouvez modifier vous-même

**Une page de doc** = un fichier MDX dans `src/content/docs/<client>/`,
nommé `NN-slug.mdx` : le préfixe numérique fixe l'ordre dans la navigation,
le reste devient l'adresse de la page. L'en-tête porte `client`, `title`,
`order`, `status`, `updated`, `description` — tous contrôlés à la
construction du site, un oubli bloque le build.

Le statut suit le cycle `draft` → `review` → `final`. Seul un humain pose
`final` : c'est la marque « relu et validé ».

**Le gabarit d'une nouvelle doc** vit dans `src/content/docs/_template/`
(visible des seuls admins) : pages canoniques à copier puis adapter,
en supprimant celles sans objet.

## Comment ça se met à jour : la skill doc-client

La doc ne s'édite pas au fil des sessions de travail — c'est ainsi que naît
une doc-journal, désordonnée et périmée. Elle se met à jour par la skill
Claude Code `doc-client` (repo `coolbeans-claude-skills`, installée dans
`~/.claude/skills/`) : la skill scanne l'état réel du projet, propose un
récapitulatif des pages à créer ou modifier, attend validation, puis écrit
en `draft`. Elle ne pose jamais `final` et ne committe jamais — relecture,
validation et commit restent des gestes humains.

Les règles d'écriture (une page par feature, profondeur progressive, langage
clair y compris sur le technique, ni actualité ni liste de tâches dans les
pages) vivent avec la skill, dans ses fichiers `references/`.

## Comment ça marche : le rendu

Les pages sont rendues à la demande (jamais prégénérées : une page statique
contournerait le contrôle d'accès). La route lit la collection, vérifie que
le lecteur a droit à cette doc (son client courant doit correspondre), et
construit la navigation, les liens précédent/suivant et l'index de recherche
à partir des pages triées par `order`. Pour un admin, l'URL gagne sur le
sélecteur de client : ouvrir la doc d'un autre client y bascule le
sélecteur.

<Callout type="piege">
  Les styles de la doc (`src/styles/doc.css`) utilisent des sélecteurs plus
  forts que les utilitaires Tailwind : une classe comme `card` y est déjà
  prise. Ne jamais réutiliser ces noms de classe dans un composant du
  portail — le style de la doc gagnerait silencieusement.
</Callout>

## Référence technique

| Élément | Emplacement |
| --- | --- |
| Contenu des docs | `src/content/docs/<client>/*.mdx`, schéma dans `src/content.config.ts` |
| Route et contrôle d'accès | `src/pages/docs/[client]/[...slug].astro` |
| Layout 3 colonnes, recherche | `src/layouts/DocLayout.astro`, composants `src/components/doc/` |
| Styles spécifiques doc | `src/styles/doc.css` |
| Entrée « Doc » du portail | `src/pages/espace/doc.astro` (redirige vers la doc du client courant) |
| Skill de mise à jour | repo `coolbeans-claude-skills`, `skills/doc-client/` |
