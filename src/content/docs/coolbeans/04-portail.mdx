L'espace connecté des clients, sur `my.coolbeans.cc`. Pour comprendre qui
voit quoi, comment un client s'ajoute, et comment les adresses propres du
portail sont servies.

## Ce que c'est

Chaque client se connecte sur `my.coolbeans.cc` et voit son espace : accueil,
doc de son projet, projets en cours, site, ressources, demandes. Les admins
voient en plus le module Chiffrages et un sélecteur pour basculer d'un client
à l'autre. Les adresses sont propres : `my.coolbeans.cc/chiffrages`, sans
préfixe technique.

Le module **Demandes** (`my.coolbeans.cc/demandes`, ex-Messagerie, renommé le
2026-09-29) est une boîte de tickets et rien d'autre. Les mails échangés avec
le client restent dans Gmail, et ses décisions vivent dans les documents
(réponses aux formulaires). L'ancienne adresse `/messagerie` redirige, y
compris celle d'un fil précis. Le fonctionnement est détaillé plus bas.

## Ce que vous pouvez modifier vous-même

**Ajouter ou modifier un client** = un fichier YAML dans
`src/content/clients/`. Le nom du fichier est l'identifiant du client. Champs :

| Champ | Rôle |
| --- | --- |
| `nom` | Nom affiché dans le portail et le sélecteur admin |
| `doc` | Identifiant de sa doc (dossier dans `src/content/docs/`). Absent, le module Doc affiche un état vide |
| `uptimerobot_monitor_ids` | Monitors de disponibilité de ses sites (prévu pour le module Site) |
| `archive` | `true` sort le client du sélecteur sans rien supprimer |

**Déclarer une indisponibilité** = une plage dans
`src/content/indisponibilites/<année>.yaml` : un premier jour, un dernier
jour (tous deux inclus) et un motif court, lu tel quel par le client. La page
Disponibilités (section Aide) affiche ces plages à tous les clients, sur six
mois glissants en calendrier complet, week-ends grisés, avec les jours fériés
français, qu'elle calcule elle-même. Le planning est commun à tous les
workspaces.

Un module dont le mapping est absent affiche un **état vide** explicite, pas
une erreur : on peut créer un client incomplet et compléter ensuite. Un
encart de diagnostic, visible des seuls admins, liste ce qui manque : c'est
le contrôle prévu par le runbook d'onboarding après la création d'un client.

## Comment ça marche

**Les adresses.** Le portail et le site partagent le même hébergement. À
l'arrivée d'une requête, le point d'entrée (`src/worker.ts`) regarde le nom
de domaine : sur `my.coolbeans.cc`, il sert en interne les pages `/espace/…`
sous des adresses courtes ; sur `coolbeans.cc`, il sert le site marketing.
Les anciennes adresses redirigent vers les canoniques. Cette réécriture vit
dans le Worker et non dans Astro, car les pages statiques du site sont
servies avant même qu'Astro ne s'exécute : seul le Worker voit tous les noms
de domaine. Staging suit le même schéma avec `staging.coolbeans.cc` et
`my-staging.coolbeans.cc`.

**L'authentification.** Better Auth protège tout `/espace` et tout `/docs`
(`src/middleware.ts`). Il est auto-hébergé : pas de fournisseur tiers, les
comptes et les sessions vivent dans la base D1 du portail. Chaque compte
porte un type (`admin`, `revendeur` ou `client`) et sa portée vient de ses
appartenances : une organisation (le revendeur) et une team (le workspace du
client), dont le slug pointe vers le registre YAML ci-dessus, qui reste la
source de vérité. Connexion par e-mail et mot de passe sur `/connexion` ;
**aucune inscription publique** : les comptes sont créés à la main.

**Une seule session pour les deux adresses.** Le site et le portail sont
deux noms de domaine, donc deux origines pour le navigateur. Le cookie de
session est posé sur `.coolbeans.cc` pour qu'une connexion ouverte sur le
portail se voie aussi sur le site : sans cet attribut, le cookie reste
attaché à l'hôte qui l'a posé, et une connexion partie de `coolbeans.cc`
laisse `my.coolbeans.cc` la redemander aussitôt. Staging partage forcément
le même domaine parent : c'est le nom du cookie qui sépare les deux
(`coolbeans-staging`), sans quoi une session de staging masquerait celle de
production. La page `/connexion` du site redirige vers celle du portail, pour
qu'il n'y ait qu'une adresse à retenir. Le bouton de la nav du site lit cette
session depuis le navigateur et devient « Mon espace » — les pages du site
sont prérendues, elles ne peuvent pas le savoir avant.

**Ouvrir un compte.** Sur `/espace/utilisateurs`, un admin crée le compte
(nom, e-mail, type, organisation, workspace) et coche « envoyer le mail » ou
non. Rien ne part sans cette case : un compte peut exister sans que personne
ne le sache, ce qui sert pendant une phase de test. Le compte ouvert n'a pas
de mot de passe : sa seule porte d'entrée est un lien magique, jusqu'à ce
qu'il s'en pose un.

Ce même lien magique sert à deux moments qui doivent lire différemment :
l'ouverture d'un accès qui n'a jamais existé, et le retour d'un compte qui
en redemande un depuis `/connexion`. L'action d'invitation pose une
métadonnée (`invitation`, `organisation`, `inviteur`) sur l'appel ; le
gabarit de mail choisi en dépend — « X vous ouvre un accès à Y » pour une
première invitation, « Votre lien de connexion » pour un retour. Sans cette
métadonnée, c'est toujours le second qui part : c'est le premier point à
vérifier si un client dit avoir reçu un mail qui ne ressemble pas à une
invitation.

**Le sélecteur admin.** Un admin choisit son « client courant » ; le choix
est mémorisé dans un cookie. Règle d'arbitrage : **l'URL gagne** : un admin
qui ouvre la doc d'un client alors que son sélecteur est ailleurs bascule
automatiquement sur ce client, pour que l'écran et le sélecteur racontent la
même chose.

**Les documents.** La page Documents d'un workspace rassemble trois natures
de documents : les fichiers déposés depuis la vue admin (devis, factures,
contrats, logos), les pages produites par le repo (cadrages et propositions
commerciales), et les liens externes (Google Docs, comptes rendus Granola).
La base ne stocke jamais le contenu, seulement la décision de le montrer.

Tout document arrive **masqué**. Le client ne voit que ce qui a été rendu
visible, ligne par ligne, d'un clic depuis la vue admin. Une ligne masquée
n'apparaît ni dans la page ni dans le HTML servi, parce que le filtre vit
dans la requête SQL, et sa route de téléchargement répond 404. Les cadrages
et les propositions du client s'enregistrent tout seuls, à chaque ouverture
de la page en vue admin ; une page retirée du repo garde sa ligne, signalée
plutôt que supprimée en silence.

**Les documents client.** Le cycle d'un projet (cadrage, proposition,
livrable, témoignage) se lit aussi à l'adresse
`my.coolbeans.cc/projets/<projet>/<étape>`. La frise du document y mène
directement, sans passer par la page publique. La page est rendue à la
demande, jamais prérendue : elle dépend de la session.

Qui lit quoi dépend de trois règles, dans cet ordre. D'abord la portée du
compte (`workspacesVisibles`) : un client ne lit que son propre
workspace, un revendeur tous ceux de son organisation, l'admin tous les
workspaces. Ensuite le statut : un client ou un revendeur ne voit que
les documents `publie`, l'admin voit aussi les brouillons. Enfin, la
proposition d'un workspace de revendeur ne se lit que par les comptes du
revendeur et par l'admin : le client final ne la voit pas. Un refus
répond toujours 404, jamais 403, pour ne pas révéler qu'un document existe.

Sur un document que le client ne peut pas lire, l'admin voit un bandeau
collé sous la barre du portail : « Brouillon · le client ne voit
pas ce document », ou « Réservé au revendeur · le client final ne
voit pas ce document » pour la proposition d'un workspace de revendeur.
Masqué à l'impression.

La barre latérale porte une section par projet du workspace courant, sous
la section Projets, le projet au document le plus récent en tête. Chaque
section liste les documents que le compte lit, libellés par leur étape
(« 2 · Proposition »).

Le champ `cle` d'une fiche client (`src/content/clients/<slug>.yaml`) relie
son workspace à la nomenclature des projets : trois lettres, reprises
de la clé de team Linear. Le build vérifie qu'elle existe dans la
nomenclature et qu'aucune clé n'est portée par deux workspaces. Un workspace
sans clé (Coolbeans, Spinoza…) n'a aucun document du cycle.

Les adresses publiques des documents restent servies telles quelles : leur
fermeture, le bouton qui publie un document depuis le portail et
l'invitation d'un compte viendront par la suite.

**Les demandes.** La page Demandes montre d'abord le formulaire, puis la
liste des fils, façon boîte de réception. Une demande porte un objet, une
description, une urgence et jusqu'à trois pièces jointes (images, PDF ou ZIP,
10 Mo chacune), vérifiées avant l'envoi puis de nouveau par le serveur. Un
fil passe en gras quand son dernier message vient de Ludo : il n'existe pas
d'état « lu » en base, c'est ce qui en tient lieu.

Chaque demande crée une issue dans la team Linear du client, avec le label
« Support », assignée à Ludo. L'urgence devient la priorité : Bloquant en
Urgent, Urgent en High, Normal en Medium, Pas pressé en Low. Le client reçoit
un accusé de réception, et Ludo une notification. Un compte ne peut pas
envoyer plus de cinq demandes par jour.

Ludo répond depuis Linear : un commentaire qui commence par l'enveloppe ✉️
(`:envelope:` au clavier) part chez le client après trois minutes de grâce,
avec un mail. Pendant ce délai, corriger le commentaire corrige le message,
et retirer l'enveloppe annule l'envoi. Un commentaire sans enveloppe reste
une note interne. Depuis le 2026-09-29, l'enveloppe remplace les chevrons
`>>`, qui ne publient plus rien. Le cron passe toutes les cinq minutes.

**Le suivi dans Linear.** La vue partagée [« Support »](https://linear.app/coolbeans-hq/view/support-78f07397ef69)
de la team Web rassemble tous les tickets du portail, tous clients et tous
projets confondus, en board avec une colonne par statut. Elle filtre sur le
label « Support ». Rattachée à la team parente, elle n'affiche les tickets
des sous-teams clients que parce que l'option d'affichage « Sub-team issues »
est active : si elle paraît vide, c'est la première chose à vérifier.

Le client ne voit pas ces colonnes. La page Demandes regroupe les statuts du
board en trois pastilles pâles :

| Statut Linear | Pastille côté client |
| --- | --- |
| Triage, Backlog, Todo | « En attente », gris |
| In Progress | « En cours », bleu |
| Done, Canceled | « Traité », vert |

Le regroupement lit le type du statut Linear, jamais son nom, qui peut
varier d'une team à l'autre. Un ticket dont l'issue est introuvable
(supprimée, pas encore rattachée) n'affiche aucune pastille.

Le client répond depuis la page du fil. Sa réponse arrive en nouveau
commentaire sur la même issue, précédé de son prénom (« **Susanne (portail)** »),
avec les liens de ses pièces jointes. Ce commentaire se place à la suite des
autres, pas en réponse imbriquée sous celui de Ludo. Linear ne notifie pas ce
commentaire, parce qu'il est posté avec la clé de Ludo : c'est un mail qui
prévient Ludo. Et ainsi de suite, une enveloppe après l'autre.

**Écrire au nom d'un client.** Un admin qui remplit le formulaire depuis
l'espace d'un client écrit au nom de ce client, sans rien à cocher. La demande
part au nom du contact principal de l'espace (le prénom noté dans sa fiche,
sinon son premier compte, jamais l'admin), comme si le client l'avait écrite.
**Aucun mail ne part**, ni au client ni à Ludo, et le quota ne s'applique pas.
L'issue Linear le dit (« Demande saisie par Ludo au nom de… »), et la base
garde la provenance. Un espace sans compte refuse l'envoi. Dans ses espaces
perso (Coolbeans, Spinoza), l'admin écrit en son nom.

Le fil ne porte pas l'étiquette « Ouvert par Ludo » ; elle est réservée
aux fils ouverts depuis Linear. Les réponses suivantes de Ludo, elles,
partent par mail comme d'habitude.

**Ouvrir un fil depuis Linear.** Poser le label « Support » sur une issue du
client ne suffit pas : il faut aussi une ligne qui commence par l'enveloppe
✉️ dans sa description. Cette ligne ouvre ce qui sera publié, jusqu'à la fin de la
description, et ce qui précède reste interne. Le fil apparaît chez le client
après le même délai de grâce, avec l'étiquette « Ouvert par Ludo » et un
mail.

**Le module Projets** est une page-souche avec état vide : l'outil de
gestion de projet est Linear, et le branchement du module sur Linear est un
chantier à part entière (voir la spec de migration dans
`docs/superpowers/specs/`).
