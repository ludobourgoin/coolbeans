L'espace connecté des clients, sur `my.coolbeans.cc`. Pour comprendre qui
voit quoi, comment un client s'ajoute, et comment les adresses propres du
portail sont servies.

## Ce que c'est

Chaque client se connecte sur `my.coolbeans.cc` et voit son espace : accueil,
doc de son projet, projets en cours, site, ressources, support. Les admins
voient en plus le module Chiffrages et un sélecteur pour basculer d'un client
à l'autre. Les adresses sont propres : `my.coolbeans.cc/chiffrages`, sans
préfixe technique.

## Ce que vous pouvez modifier vous-même

**Ajouter ou modifier un client** = un fichier YAML dans
`src/content/clients/`. Le nom du fichier est l'identifiant du client. Champs :

| Champ | Rôle |
| --- | --- |
| `nom` | Nom affiché dans le portail et le sélecteur admin |
| `doc` | Identifiant de sa doc (dossier dans `src/content/docs/`). Absent, le module Doc affiche un état vide |
| `uptimerobot_monitor_ids` | Monitors de disponibilité de ses sites (prévu pour le module Site) |
| `archive` | `true` sort le client du sélecteur sans rien supprimer |

**Déclarer une indisponibilité** = une plage dans
`src/content/indisponibilites/<année>.yaml` : un premier jour, un dernier
jour (tous deux inclus) et un motif court, lu tel quel par le client. La page
Disponibilités (section Aide) affiche ces plages à tous les clients, sur six
mois glissants en calendrier complet, week-ends grisés, avec les jours fériés
français, qu'elle calcule elle-même. Le planning est commun à tous les
workspaces.

Un module dont le mapping est absent affiche un **état vide** explicite, pas
une erreur : on peut créer un client incomplet et compléter ensuite. Un
encart de diagnostic, visible des seuls admins, liste ce qui manque : c'est
le contrôle prévu par le runbook d'onboarding après la création d'un client.

## Comment ça marche

**Les adresses.** Le portail et le site partagent le même hébergement. À
l'arrivée d'une requête, le point d'entrée (`src/worker.ts`) regarde le nom
de domaine : sur `my.coolbeans.cc`, il sert en interne les pages `/espace/…`
sous des adresses courtes ; sur `coolbeans.cc`, il sert le site marketing.
Les anciennes adresses redirigent vers les canoniques. Cette réécriture vit
dans le Worker et non dans Astro, car les pages statiques du site sont
servies avant même qu'Astro ne s'exécute : seul le Worker voit tous les noms
de domaine. Staging suit le même schéma avec `staging.coolbeans.cc` et
`my-staging.coolbeans.cc`.

**L'authentification.** Better Auth protège tout `/espace` et tout `/docs`
(`src/middleware.ts`). Il est auto-hébergé : pas de fournisseur tiers, les
comptes et les sessions vivent dans la base D1 du portail. Chaque compte
porte un type (`admin`, `revendeur` ou `client`) et sa portée vient de ses
appartenances : une organisation (le revendeur) et une team (le workspace du
client), dont le slug pointe vers le registre YAML ci-dessus, qui reste la
source de vérité. Connexion par e-mail et mot de passe sur `/connexion` ;
**aucune inscription publique** : les comptes sont créés à la main.

**Une seule session pour les deux adresses.** Le site et le portail sont
deux noms de domaine, donc deux origines pour le navigateur. Le cookie de
session est posé sur `.coolbeans.cc` pour qu'une connexion ouverte sur le
portail se voie aussi sur le site : sans cet attribut, le cookie reste
attaché à l'hôte qui l'a posé, et une connexion partie de `coolbeans.cc`
laisse `my.coolbeans.cc` la redemander aussitôt. Staging partage forcément
le même domaine parent : c'est le nom du cookie qui sépare les deux
(`coolbeans-staging`), sans quoi une session de staging masquerait celle de
production. La page `/connexion` du site redirige vers celle du portail, pour
qu'il n'y ait qu'une adresse à retenir. Le bouton de la nav du site lit cette
session depuis le navigateur et devient « Mon espace » — les pages du site
sont prérendues, elles ne peuvent pas le savoir avant.

**Ouvrir un compte.** Sur `/espace/utilisateurs`, un admin crée le compte
(nom, e-mail, type, organisation, workspace) et coche « envoyer le mail » ou
non. Rien ne part sans cette case : un compte peut exister sans que personne
ne le sache, ce qui sert pendant une phase de test. Le compte ouvert n'a pas
de mot de passe : sa seule porte d'entrée est un lien magique, jusqu'à ce
qu'il s'en pose un.

Ce même lien magique sert à deux moments qui doivent lire différemment :
l'ouverture d'un accès qui n'a jamais existé, et le retour d'un compte qui
en redemande un depuis `/connexion`. L'action d'invitation pose une
métadonnée (`invitation`, `organisation`, `inviteur`) sur l'appel ; le
gabarit de mail choisi en dépend — « X vous ouvre un accès à Y » pour une
première invitation, « Votre lien de connexion » pour un retour. Sans cette
métadonnée, c'est toujours le second qui part : c'est le premier point à
vérifier si un client dit avoir reçu un mail qui ne ressemble pas à une
invitation.

**Le sélecteur admin.** Un admin choisit son « client courant » ; le choix
est mémorisé dans un cookie. Règle d'arbitrage : **l'URL gagne** : un admin
qui ouvre la doc d'un client alors que son sélecteur est ailleurs bascule
automatiquement sur ce client, pour que l'écran et le sélecteur racontent la
même chose.

**Les documents.** La page Documents d'un workspace rassemble trois natures
de documents : les fichiers déposés depuis la vue admin (devis, factures,
contrats, logos), les pages produites par le repo (cadrages et propositions
commerciales), et les liens externes (Google Docs, comptes rendus Granola).
La base ne stocke jamais le contenu, seulement la décision de le montrer.

Tout document arrive **masqué**. Le client ne voit que ce qui a été rendu
visible, ligne par ligne, d'un clic depuis la vue admin. Une ligne masquée
n'apparaît ni dans la page ni dans le HTML servi, parce que le filtre vit
dans la requête SQL, et sa route de téléchargement répond 404. Les cadrages
et les propositions du client s'enregistrent tout seuls, à chaque ouverture
de la page en vue admin ; une page retirée du repo garde sa ligne, signalée
plutôt que supprimée en silence.

**Le module Projets** est une page-souche avec état vide : l'outil de
gestion de projet est Linear, et le branchement du module sur Linear est un
chantier à part entière (voir la spec de migration dans
`docs/superpowers/specs/`).

## Référence technique

| Élément | Emplacement |
| --- | --- |
| Réécriture d'hôte et redirections | `src/worker.ts`, règles `run_worker_first` dans `wrangler.jsonc` |
| Protection des routes privées | `src/middleware.ts` |
| Authentification (instance, options, session) | `src/lib/auth/server.ts`, `options.ts`, `session.ts` |
| Ouverture de compte et choix du mail d'invitation | `src/actions/index.ts` (`utilisateurs.inviter`), `src/lib/portail/utilisateurs.ts` |
| Gabarits des mails d'authentification | `src/emails/auth.ts` (`renderInvitation`, `renderLienMagique`, `renderReinitialisation`) |
| Page de connexion et menu compte | `src/pages/connexion.astro`, `src/components/portail/PortalNav.astro` |
| Session partagée site / portail | `src/lib/auth/options.ts` (`cookiesPartages`), `src/components/Nav.astro` |
| Comptes rattachés à un workspace | `src/lib/portail/comptes.ts` |
| Registre des workspaces | `src/content/clients/*.yaml`, schéma dans `src/content.config.ts`, lecture dans `src/lib/portail/workspaces.ts` |
| Lecture métadonnées / workspace courant | `src/lib/portail/metadata.ts`, `current-workspace.ts`, `context.ts` |
| Sélecteur de workspace (admin) | `src/components/portail/WorkspaceSwitcher.astro`, en tête de `PortalSidebar.astro` |
| Navigation et retours | `src/lib/portail/nav.ts`, `retour.ts` |
| Garde admin (pages et actions) | `src/lib/portail/require-admin.ts` |
| Pages des modules | `src/pages/espace/*.astro` |
| États vides et diagnostic | `src/components/portail/EmptyState.astro`, `missingKeysFor` dans `src/lib/portail/workspaces.ts` |
